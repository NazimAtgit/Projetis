Git et GitHub, du premier commit au retour en arrière

Ce guide accompagne le tutoriel obligatoire de l'Atelier. Lisez les chapitres 1 à 9 avant de commencer, gardez l'aide-mémoire ouvert pendant le projet, et faites les exercices avec votre binôme.

01

Git et GitHub, c'est quoi ?

Vous avez sûrement déjà eu un dossier qui ressemble à ça : rapport_v2.docx, rapport_v3_corrige.docx, rapport_FINAL.docx, rapport_FINAL_vraiment.docx. Personne ne sait plus quelle version est la bonne ni ce qui a changé entre deux. Git règle exactement ce problème.

GitUn logiciel installé sur votre ordinateur. Il enregistre l'historique complet de votre projet : chaque version, qui l'a faite, quand et pourquoi. Il fonctionne sans Internet.
GitHubUn site web qui héberge une copie de votre projet Git. Il sert de sauvegarde en ligne et de point de rencontre : votre binôme et votre encadrant y voient le même projet que vous.

Git est l'outil, GitHub est le lieu de partage. On peut utiliser Git sans GitHub (seul, sur son PC), mais pour un projet à deux, on utilise les deux. Il existe d'autres sites du même genre (GitLab, Bitbucket) ; les commandes Git sont identiques.

02

À quoi ça sert, concrètement

Revenir en arrièreVotre firmware ESP32 marchait hier et plus aujourd'hui ? Vous retrouvez la version d'hier en une commande, et vous voyez ligne par ligne ce qui a changé.
Travailler à deux sans s'écraserChacun travaille sur sa copie. Git fusionne vos modifications, même sur le même fichier, et vous prévient seulement s'il y a un vrai désaccord.
SauvegardeUn PC volé ou une clé USB perdue ne coûte plus le projet : tout est sur GitHub.
Savoir qui a fait quoiChaque modification porte un nom et une date. L'encadrant voit la part de chacun, et vous retrouvez pourquoi une ligne a été écrite.
Essayer sans risqueUne idée risquée se teste sur une branche. Si elle échoue, on la supprime ; la version qui marche n'a jamais été touchée.
Un atout pour votre CVGit est utilisé dans presque toutes les entreprises du logiciel et de l'embarqué. Un profil GitHub avec de vrais projets se montre en entretien.
03

Le vocabulaire

Les mots sont en anglais dans les commandes ; voici ce qu'ils veulent dire.

dépôt (repo)
Le dossier du projet suivi par Git, avec tout son historique (caché dans un sous-dossier .git).
commit
Une version enregistrée du projet : une « photo » des fichiers, avec un message, un auteur, une date et un identifiant (ex. a1b2c3d).
branche
Une ligne de travail parallèle. La branche principale s'appelle main.
HEAD
« Vous êtes ici » : le commit sur lequel vous travaillez en ce moment.
remote / origin
La copie du dépôt sur GitHub. origin est son nom par défaut.
clone
Télécharger un dépôt GitHub sur votre ordinateur, historique compris.
push
Envoyer vos commits vers GitHub.
pull
Récupérer les commits des autres depuis GitHub.
merge
Fusionner une branche dans une autre.
pull request (PR)
Sur GitHub, une demande de fusion d'une branche, que votre binôme relit avant d'accepter.
conflit
Deux modifications incompatibles de la même ligne ; Git vous demande de choisir.
tag
Une étiquette posée sur un commit important, par exemple v1.0-mvp.
04

Les trois zones de Git

C'est l'idée la plus importante du guide. Un fichier modifié ne part pas directement sur GitHub : il passe par trois étapes, chacune déclenchée par une commande.

Pourquoi un index ? Parce qu'on ne veut pas toujours tout enregistrer d'un coup. Vous avez modifié le code du GPS et le rapport : vous pouvez faire un commit pour le code, puis un autre pour le rapport. Deux commits clairs valent mieux qu'un commit fourre-tout.

05

Installer et configurer

  1. Créez un compte sur github.com avec votre adresse étudiante, et envoyez votre nom d'utilisateur à l'encadrant.

  2. Installez Git depuis git-scm.com. Sous Windows, gardez les options par défaut : vous obtenez « Git Bash », un terminal où taper les commandes. Sous Linux : sudo apt install git. Sous macOS : xcode-select --install.

  3. Présentez-vous à Git, une seule fois par ordinateur. Mettez la même adresse que sur GitHub, sinon vos commits ne seront pas reliés à votre profil.

    git config --global user.name "Prénom Nom"
git config --global user.email "votre.adresse@exemple.dz"
git config --global init.defaultBranch main
git --version            # vérifie l'installation
Sans terminal ?VS Code (onglet « Source Control ») et GitHub Desktop font les mêmes opérations avec des boutons. Apprenez quand même les commandes : elles fonctionnent partout et c'est ce qui sera demandé en soutenance.
06

Récupérer le dépôt du projet

L'encadrant a créé le dépôt de votre groupe et vous a invité. Acceptez l'invitation (e-mail ou github.com/notifications), puis sur la page du dépôt cliquez sur le bouton vert Code et copiez l'adresse HTTPS.

cd ~/Documents                        # là où vous rangez vos projets
git clone https://github.com/ORGANISATION/p1-bus-gps.git
cd p1-bus-gps
git status

Au premier push, une fenêtre de navigateur s'ouvre pour vous connecter à GitHub : acceptez. GitHub n'accepte plus le mot de passe du compte dans le terminal ; si on vous le demande quand même, utilisez un « personal access token » (Settings → Developer settings).

Créer un dépôt soi-mêmePour un projet personnel : git init dans un dossier existant, puis créez un dépôt vide sur GitHub et suivez les deux commandes que GitHub affiche (git remote add origin … puis git push -u origin main).
07

Le cycle de tous les jours

À chaque séance de travail, la même routine :

git pull                          # 1. récupérer le travail du binôme
#    … vous modifiez vos fichiers …
git status                        # 2. voir ce qui a changé
git diff                          # 3. relire vos modifications ligne par ligne
git add firmware/gps.cpp          # 4. choisir les fichiers du commit
git commit -m "Ajoute la lecture des trames NMEA"   # 5. enregistrer la version
git push                          # 6. envoyer sur GitHub

git add . ajoute tous les fichiers modifiés du dossier courant. C'est pratique, mais relisez git status avant : c'est comme ça qu'on envoie par erreur un mot de passe Wi-Fi ou 200 Mo de fichiers de compilation.

Écrire un bon message de commit

À éviterÀ faire
updateAjoute la détection de pic sur le piézo 1
fixCorrige le double déclenchement avec un temps mort de 30 ms
modifs du mardiRédige la partie conception du rapport

La règle : un verbe au présent, puis ce que fait le commit, en moins de 70 caractères. Dans trois semaines, c'est ce message qui vous permettra de retrouver la bonne version.

Combien de commits ?Un commit par étape qui fonctionne, souvent plusieurs par séance. Un petit commit se comprend et s'annule facilement ; un commit de toute une semaine, non.
08

Lire l'historique

git log --oneline --graph --all   # l'historique, un commit par ligne
* 7f3c2e1 (HEAD -> main, origin/main) Ajoute le calcul du temps d'arrivée
* 4b9a0d8 Affiche la position sur la carte Leaflet
* a1b2c3d Ajoute la lecture des trames NMEA
* 0e5f6a7 Premier commit : structure du dépôt
git show a1b2c3d                  # ce qu'a changé un commit précis
git diff a1b2c3d 7f3c2e1          # différences entre deux versions
git log -- firmware/gps.cpp       # l'historique d'un seul fichier
git blame firmware/gps.cpp        # qui a écrit chaque ligne, et dans quel commit

L'identifiant (a1b2c3d) désigne une version de façon unique. Les 7 premiers caractères suffisent. On peut aussi compter depuis la position actuelle : HEAD~1 est le commit d'avant, HEAD~3 celui d'il y a trois commits.

Sur GitHub, le même historique est dans l'onglet Commits du dépôt ; sur un fichier, les boutons History et Blame font la même chose que les commandes ci-dessus.

09

Revenir en arrière

C'est la raison d'être de Git. La bonne commande dépend de deux questions : la modification est-elle déjà enregistrée dans un commit ? et ce commit est-il déjà sur GitHub ?

SituationCommandeRisque
J'ai cassé un fichier et je veux le remettre comme au dernier commitgit restore fichierperd les modifs du fichier
J'ai fait git add sur un fichier par erreurgit restore --staged fichiersans risque
Je veux mettre mes modifications de côté pour faire un pullgit stash puis git stash popsans risque
Mon dernier commit a un mauvais message ou un fichier oublié (pas encore poussé)git add oubli.cpp
git commit --amend		sans risque
Je veux récupérer un fichier tel qu'il était dans un ancien commitgit restore --source a1b2c3d fichierremplace le fichier actuel
Je veux juste regarder ou tester une ancienne versiongit switch --detach a1b2c3d
puis git switch main		sans risque
Un commit déjà sur GitHub a cassé le projetgit revert 7f3c2e1
git push		sans risque
Je veux effacer mes derniers commits, pas encore poussésgit reset --hard a1b2c3defface le travail
J'ai fait un reset et je veux retrouver un commit « perdu »git reflog puis git reset --hard IDà faire vite

revert ou reset : la différence qui compte

La règle d'orCe qui est déjà sur GitHub ne s'efface pas : on l'annule avec git revert. Réservez git reset --hard, git commit --amend et git push --force aux commits qui ne sont encore que sur votre ordinateur.

Exemple complet : le firmware ne marche plus

git log --oneline                     # repérer les derniers commits
7f3c2e1 Passe le GPS à 10 Hz
4b9a0d8 Ajoute le mode économie d'énergie
a1b2c3d Lecture NMEA stable
git switch --detach a1b2c3d           # tester l'ancienne version : flasher l'ESP32
git switch main                       # revenir au présent
git revert 7f3c2e1                    # le coupable est 7f3c2e1 : on l'annule
git push
10

Marquer des versions

Chaque commit est une version, mais certaines comptent plus que d'autres : celle présentée à la démo technique, le MVP, la version de soutenance. On leur pose un tag, une étiquette qui ne bouge plus.

git tag -a v0.4-demo -m "Démo technique de la semaine 4"
git push origin v0.4-demo             # les tags ne partent pas avec un push normal
git tag                               # liste des versions
git switch --detach v0.4-demo         # revenir exactement à la version de la démo
git diff v0.4-demo v1.0-mvp           # tout ce qui a changé entre les deux

Pour l'Atelier, utilisez ces noms aux jalons : v0.1-cdc (cahier des charges, S1), v0.4-demo (S4), v1.0-mvp (S6), v1.1-final (S8). Sur GitHub, transformez un tag en Release (onglet Releases → Draft a new release) pour y joindre le binaire du firmware, l'APK de l'application ou le PDF du rapport.

Astuce embarquéAffichez la version dans le firmware au démarrage (Serial.println("bus-gps v1.0-mvp");). Quand une carte se comporte bizarrement, vous savez immédiatement quel code elle contient.
11

Branches et pull requests

La branche main doit toujours contenir une version qui marche. Chaque tâche se fait sur sa propre branche, et n'arrive dans main qu'après relecture par le binôme.

git switch main
git pull
git switch -c sarah/carte-leaflet      # nouvelle branche pour la tâche
# … commits …
git push -u origin sarah/carte-leaflet # premier envoi de la branche

  1. Sur GitHub, cliquez sur Compare & pull request. Titre = le résultat de la tâche ; description = ce qui a été fait et comment le tester.

  2. Le binôme relit l'onglet Files changed, commente si besoin, puis clique sur Merge pull request.

  3. Chacun revient sur main et récupère la fusion :

    git switch main
git pull
git branch -d sarah/carte-leaflet      # supprimer la branche terminée

Nommez les branches prénom/sujet-court : on sait tout de suite à qui elles sont et ce qu'elles contiennent.

12

Résoudre un conflit

Un conflit arrive quand vous et votre binôme avez modifié la même ligne du même fichier. Ce n'est pas une erreur : Git refuse simplement de choisir à votre place. Il l'indique au pull ou au merge :

CONFLICT (content): Merge conflict in firmware/config.h
Automatic merge failed; fix conflicts and then commit the result.

Dans le fichier, Git a placé les deux versions entre des marques :

<<<<<<< HEAD
#define SEUIL_PIEZO 180        // votre version
=======
#define SEUIL_PIEZO 220        // la version du binôme
>>>>>>> origin/main

  1. Discutez avec votre binôme pour savoir quelle valeur garder (ou combinez les deux).

  2. Modifiez le fichier pour qu'il ne reste que la bonne version, sans les marques <<<, ===, >>>.

  3. git add firmware/config.h
git commit                             # Git propose un message de fusion
git push

Pour abandonner et revenir à l'état d'avant : git merge --abort. Pour en avoir moins : faites git pull avant de commencer, des commits petits et fréquents, et répartissez-vous les fichiers.

13

Ce qu'on ne met pas dans Git

Git sert au code source et aux documents que vous écrivez, pas à ce qui est généré automatiquement ni aux secrets. Créez à la racine du dépôt un fichier .gitignore :

# Compilation (PlatformIO, Arduino, IDE)
.pio/
build/
*.bin
*.elf
.vscode/
# Web et applications
node_modules/
dist/
# Système
.DS_Store
Thumbs.db
# Secrets : JAMAIS dans Git
secrets.h
.env
Mots de passe Wi-Fi, clés d'API, identifiants de base de donnéesUn dépôt public est lu par des robots qui cherchent ces informations en permanence, et un secret reste visible dans l'historique même après suppression du fichier. Mettez-les dans secrets.h (ignoré), et versionnez à la place un secrets.example.h avec des valeurs factices. Si un secret a été poussé par erreur, changez-le immédiatement.
// secrets.example.h — à copier en secrets.h et à remplir
#define WIFI_SSID     "nom-du-reseau"
#define WIFI_PASSWORD "mot-de-passe"

Fichier déjà suivi par erreur ? git rm --cached secrets.h, ajoutez-le au .gitignore, puis faites un commit. Les grosses vidéos et fichiers de plus de 50 Mo n'ont pas leur place dans Git non plus : déposez-les dans une Release ou un lien dans le README.

16

Exercices en binôme

À faire dans le dépôt du groupe, sur une branche exercices que vous supprimerez ensuite. Comptez 30 minutes.

Exercice 1 · Revenir en arrière

  1. Créez essai.txt avec la ligne « version 1 », faites un commit.
  2. Remplacez par « version 2 », faites un commit et un push.
  3. Avec git revert, revenez à « version 1 » sans effacer l'historique. Vérifiez avec git log --oneline : combien de commits voyez-vous ?

Exercice 2 · Retrouver une ancienne version d'un fichier

  1. Avec git log --oneline -- essai.txt, trouvez l'identifiant du commit « version 2 ».
  2. Récupérez ce contenu avec git restore --source ID essai.txt, puis faites un commit.

Exercice 3 · Provoquer et résoudre un conflit

  1. Chacun modifie la même ligne de essai.txt sur son ordinateur, sans faire de pull.
  2. Le premier fait commit + push. Le second fait commit, puis git pull : le conflit apparaît.
  3. Résolvez-le ensemble (chapitre 12), puis commit et push.

Exercice 4 · Poser un tag

  1. Posez le tag v0.0-exercices et poussez-le.
  2. Sur GitHub, trouvez-le dans l'onglet Tags et créez une Release à partir de lui.
